Вчера вы описывали данные. Сегодня — поведение. Интерфейсы в Go устроены иначе, чем в TypeScript или Java, и главное отличие в одном слове: **неявно**. Тип нигде не объявляет, что реализует интерфейс. Если методы совпали — он его реализует.

## Чтение

- [ ] [Tour of Go — Interfaces](https://go.dev/tour/methods/9) — слайды 9–18, включая `nil`-значения интерфейсов и `Stringer`
- [ ] [Go Code Review Comments — Interfaces](https://go.dev/wiki/CodeReviewComments#interfaces) — три абзаца, но это главное правило проектирования

Что унести:

- Интерфейс — это **набор сигнатур методов**. Ключевого слова `implements` нет
- **Интерфейс объявляется на стороне потребителя**, а не рядом с реализацией. Тот, кто вызывает, описывает, что ему нужно
- Чем меньше интерфейс, тем он полезнее. `io.Writer` — один метод, и на нём держится половина стандартной библиотеки
- Принимайте интерфейс, возвращайте конкретный тип
- Интерфейс с одним методом принято называть по методу с суффиксом `-er`: `Writer`, `Reader`, `Stringer`
- **Значение интерфейса — это пара (тип, значение).** Отсюда растёт самая коварная ошибка в языке, увидите её в эксперименте В
- Если методы объявлены с ресивером-указателем, интерфейс реализует только `*T`, но не `T`. Вот зачем вчерашнее правило консистентности

### Задача 1. Эксперименты

Файл `<ваше-имя>/week02/day02/experiments/main.go`.

**А. Неявная реализация.**

```go
type Greeter interface {
	Greet() string
}

type Russian struct{}
func (r Russian) Greet() string { return "Привет" }

type Japanese struct{}
func (j Japanese) Greet() string { return "こんにちは" }

func main() {
	greeters := []Greeter{Russian{}, Japanese{}}
	for _, g := range greeters {
		fmt.Println(g.Greet())
	}
}
```

Нигде не написано, что `Russian` реализует `Greeter`. Типы даже не знают о существовании интерфейса.

**Б. Множество методов.**

```go
type Counter struct{ n int }
func (c *Counter) Greet() string { c.n++; return fmt.Sprint("привет №", c.n) }

var g Greeter = Counter{}     // не скомпилируется
var g Greeter = &Counter{}    // а так да
```

Раскомментируйте первую строку, прочитайте ошибку целиком. Она объясняет разницу между множествами методов `T` и `*T`.

**В. Главная ловушка языка.**

```go
type MyError struct{}

func (e *MyError) Error() string { return "что-то сломалось" }

func mayFail(fail bool) error {
	var err *MyError
	if fail {
		err = &MyError{}
	}
	return err          // ← вот здесь проблема
}

func main() {
	err := mayFail(false)
	fmt.Println(err)          // <nil>
	fmt.Println(err == nil)   // предскажите!
}
```

Печатается `<nil>`, а сравнение с `nil` даёт `false`. Причина: интерфейс — пара (тип, значение), и тип в ней `*MyError`, даже когда значение нулевое. Непустая половина делает пару непустой.

**Как правильно:** не возвращайте конкретный тип указателя как `error`. Возвращайте `nil` явно:

```go
func mayFail(fail bool) error {
	if !fail {
		return nil
	}
	return &MyError{}
}
```

Эту ошибку ловит `golangci-lint` линтером `nilness`, но не `go vet` в базовой настройке.

**Г. Приведение типа и тип-свитч.**

```go
var g Greeter = Russian{}

if r, ok := g.(Russian); ok {
	fmt.Println("это русский:", r.Greet())
}

switch v := g.(type) {
case Russian:
	fmt.Println("Russian:", v.Greet())
case Japanese:
	fmt.Println("Japanese:", v.Greet())
default:
	fmt.Println("кто-то ещё")
}
```

Форма без `ok` — `g.(Japanese)` — при несовпадении паникует. Проверьте.

### Задача 2. Счётчик записанных байт

Тип, который оборачивает любой `io.Writer` и считает, сколько через него прошло. Классический паттерн-декоратор — вы встретите его на одиннадцатой неделе, когда будете собирать метрики HTTP.

Интерфейс `io.Writer` состоит ровно из одного метода:

```go
type Writer interface {
	Write(p []byte) (n int, err error)
}
```

- [ ] Создать `<ваше-имя>/week02/day02/countingwriter/main.go`:

```go
package main

import (
	"fmt"
	"io"
	"os"
	"strings"
)

// CountingWriter оборачивает io.Writer и считает,
// сколько байт и сколько вызовов Write через него прошло.
type CountingWriter struct {
	w      io.Writer
	bytes  int64
	writes int
}

// проверка на этапе компиляции, что интерфейс реализован
var _ io.Writer = (*CountingWriter)(nil)

func NewCountingWriter(w io.Writer) *CountingWriter {
	// ваш код
}

func (c *CountingWriter) Write(p []byte) (int, error) {
	// ваш код:
	// 1) записать во вложенный writer
	// 2) прибавить РЕАЛЬНО записанное количество байт, а не len(p)
	// 3) вернуть то, что вернул вложенный writer
}

func (c *CountingWriter) Bytes() int64 { return c.bytes }
func (c *CountingWriter) Writes() int  { return c.writes }

func main() {
	// 1. Оборачиваем стандартный вывод
	cw := NewCountingWriter(os.Stdout)

	fmt.Fprintln(cw, "Привет, интерфейсы!")
	fmt.Fprintf(cw, "Сегодня %d-й день второй недели\n", 2)

	fmt.Printf("\nзаписано: %d байт за %d вызовов\n", cw.Bytes(), cw.Writes())

	// 2. Тот же тип работает с любым writer'ом
	var sb strings.Builder
	cw2 := NewCountingWriter(&sb)
	io.Copy(cw2, strings.NewReader("строка из ридера"))
	fmt.Printf("в builder: %d байт, содержимое: %q\n", cw2.Bytes(), sb.String())
}
```

**Требования:**

- [ ] `Write` возвращает ровно то, что вернул вложенный `io.Writer` — и число, и ошибку. Не подменяйте
- [ ] Счётчик увеличивается на `n`, а не на `len(p)`. При ошибке вложенный writer мог записать часть
- [ ] Компиляционная проверка `var _ io.Writer = (*CountingWriter)(nil)` остаётся в файле. Это идиома: если сигнатура разъедется, ошибка будет на этой строке, а не в далёком месте использования

**Проверка:**

- [ ] Текст печатается в консоль как обычно — обёртка прозрачна
- [ ] `Привет, интерфейсы!` со переводом строки — это 32 байта, а не 19: кириллица по два байта на букву (привет пятому дню первой недели)
- [ ] Второй пример пишет в `strings.Builder` без единого изменения в `CountingWriter`

**Если успели, попробуйте третий случай:**

```go
cw3 := NewCountingWriter(io.MultiWriter(os.Stdout, &sb))
fmt.Fprintln(cw3, "в два места сразу")
```

`io.MultiWriter` — сам по себе `io.Writer`, который пишет в несколько. Всё складывается как конструктор именно потому, что интерфейс маленький.

## Частые грабли

**Интерфейс объявлен рядом с реализацией.** Привычка из Java и C#. В Go интерфейс принадлежит тому, кто его использует: пакет, которому нужно куда-то писать, объявляет у себя `Writer` с одним методом. Реализация о нём не знает. Это то, что делает код по-настоящему развязанным.

**Слишком большой интерфейс.** Интерфейс на восемь методов не даёт ничего: подменить его в тесте так же тяжело, как и конкретный тип. Есть проверенное правило — чем больше интерфейс, тем слабее абстракция.

**Возврат интерфейса из конструктора.** `func New() Storer` лишает вызывающего доступа ко всему, чего нет в интерфейсе. Возвращайте `*PostgresStore`, а интерфейс пусть объявит тот, кто принимает.

**`nil`-указатель в интерфейсе.** Эксперимент В. Встречается в реальном коде в виде `func f() *MyError` с последующим присваиванием в переменную типа `error`. Симптом: `if err != nil` срабатывает там, где ошибки нет.

**Забытый `&` при передаче.** Если методы с ресивером-указателем, `SomeFunc(myValue)` не скомпилируется — нужно `SomeFunc(&myValue)`. Ошибка компилятора при этом длинная и пугающая, но говорит ровно об этом.

**`any` вместо интерфейса.** `func process(v any)` — это отказ от типизации. Внутри придётся делать тип-свитч, и компилятор перестаёт вам помогать. Иногда оправданно (`fmt.Println` принимает `any`), но в своём коде это почти всегда признак недодуманного дизайна.
