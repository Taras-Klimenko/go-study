# Неделя 2, День 1 — структуры и методы

**Время:** 60 минут
**Цель:** научиться описывать типы данных и понять главный выбор дня — ресивер по значению или по указателю.

Вторая неделя про то, как в Go устроена абстракция. Начинаем с фундамента: структура — это единственный способ собрать несколько значений в одно целое. Классов нет, наследования нет, `this` нет.

## 0–10 мин. Чтение

- [ ] [Go Code Review Comments — Receiver Type](https://go.dev/wiki/CodeReviewComments#receiver-type) — короткий, но это и есть ответ на главный вопрос дня

Что унести:

**Структуры**
- Нулевое значение структуры — все поля в нулях. Работать с ней можно сразу, без конструктора
- Литерал лучше писать с именами полей: `Item{ID: 1, Title: "x"}`. Позиционный `Item{1, "x"}` сломается при добавлении поля
- Структуры **копируются при присваивании и передаче в функцию** — это значимый тип, как массив
- `==` работает, если все поля сравнимы. Структура со срезом внутри не сравнима — ошибка компиляции

**Методы**
- Метод — обычная функция с ресивером: `func (l *List) Add(...)`. Никакого `this` или `self`
- Ресивер называют одной-двумя буквами по имени типа: `l` для `List`, `c` для `Counter`
- **По указателю** — если метод меняет состояние или структура большая
- **По значению** — для маленьких неизменяемых типов
- **Смешивать нельзя.** Если хотя бы один метод типа с указателем, делайте с указателем все
- Go сам берёт адрес: у переменной `c` можно вызвать `c.Inc()`, даже если ресивер `*Counter`

### Задача 1. Эксперименты (≈15 мин)

Файл `<ваше-имя>/week02/day01/experiments/main.go`. Как обычно: предсказание, потом запуск.

**А. Нулевое значение и копирование.**

```go
type Point struct {
	X, Y int
}

var p Point
fmt.Println(p)        // работает без инициализации

q := p
q.X = 99
fmt.Println(p, q)     // что стало с p?
```

**Б. Главный эксперимент дня.**

```go
type Counter struct {
	N int
}

func (c Counter) IncValue()   { c.N++ }   // ресивер по значению
func (c *Counter) IncPointer() { c.N++ }  // ресивер по указателю

func main() {
	c := Counter{}

	c.IncValue()
	c.IncValue()
	fmt.Println("после IncValue:", c.N)

	c.IncPointer()
	c.IncPointer()
	fmt.Println("после IncPointer:", c.N)
}
```

Предскажите оба числа. Это самая частая ошибка новичков в Go — и компилятор о ней молчит, потому что формально всё корректно.

**В. Автоматическое взятие адреса.**

Обратите внимание: вы написали `c.IncPointer()`, а не `(&c).IncPointer()`. Компилятор подставил адрес сам. Проверьте, что будет здесь:

```go
counters := map[string]Counter{"a": {}}
counters["a"].IncPointer()   // не скомпилируется — почему?
```

Вспомните прошлую тему: элемент мапы не адресуем.

**Г. Копия в range.**

```go
points := []Point{{1, 1}, {2, 2}}
for _, pt := range points {
	pt.X = 100
}
fmt.Println(points)   // изменилось?
```

Тот же механизм, что и в первую неделю со слайсами. Как починить — два способа.

**Д. Сравнение структур.**

```go
fmt.Println(Point{1, 2} == Point{1, 2})

// fmt.Println(Bag{} == Bag{})   // раскомментируйте и прочитайте ошибку
```

```go
package main

import (
	"errors"
	"fmt"
)

var ErrNotFound = errors.New("элемент не найден")

type Item struct {
	ID    int
	Title string
	Done  bool
}

type List struct {
	Name   string
	items  []Item
	nextID int
}

// NewList создаёт список с заданным именем.
func NewList(name string) *List {
	// ваш код
}

// Add добавляет элемент и возвращает его ID.
func (l *List) Add(title string) int {
	// ваш код
}

// Complete помечает элемент выполненным.
// Возвращает ErrNotFound, если элемента с таким ID нет.
func (l *List) Complete(id int) error {
	// ваш код
}

// Remove удаляет элемент по ID.
func (l *List) Remove(id int) error {
	// ваш код
}

// Pending возвращает невыполненные элементы.
func (l *List) Pending() []Item {
	// ваш код
}

func main() {
	list := NewList("Учёба")

	goID := list.Add("Дочитать про методы")
	list.Add("Решить задачу на Exercism")
	list.Add("Сделать ревью")

	if err := list.Complete(goID); err != nil {
		fmt.Println("ошибка:", err)
	}

	if err := list.Complete(999); err != nil {
		fmt.Println("ожидаемая ошибка:", err)
	}

	fmt.Printf("Список %q, осталось %d:\n", list.Name, len(list.Pending()))
	for _, it := range list.Pending() {
		fmt.Printf("  [%d] %s\n", it.ID, it.Title)
	}
}
```

**Требования:**

| Метод | Поведение |
|---|---|
| `NewList` | Возвращает `*List` с `nextID`, равным 1 |
| `Add` | Присваивает `nextID`, инкрементирует счётчик, возвращает выданный ID |
| `Complete` | Меняет `Done` на `true`; на неизвестный ID — `ErrNotFound` |
| `Remove` | Удаляет элемент; на неизвестный ID — `ErrNotFound` |
| `Pending` | Возвращает только невыполненные, исходный срез не мутирует |

Обратите внимание на детали:

- [ ] Поля `items` и `nextID` с маленькой буквы — они неэкспортируемые. Снаружи пакета до них не добраться, менять список можно только через методы
- [ ] Все методы с ресивером-указателем, включая `Pending`, который ничего не меняет. Это правило консистентности из чтения
- [ ] В `Complete` цикл должен идти по индексу: `for i := range l.items`. Через `for _, it := range` вы получите копию, и `it.Done = true` ничего не сделает
- [ ] В `Remove` пригодится `slices.Delete` или ручной `append(l.items[:i], l.items[i+1:]...)`

- [ ] `Complete(999)` вернул ошибку, а не запаниковал

## Частые грабли

**Ресивер по значению у метода, который меняет состояние.** Компилируется, работает, ничего не делает. Ошибка находится отладочной печатью через полчаса. Правило: сомневаетесь — берите указатель.

**Смешение ресиверов у одного типа.** Половина методов по значению, половина по указателю. Формально законно, но приводит к неочевидному поведению при работе через интерфейсы — завтра увидите, почему.

**`for _, x := range` при попытке изменить элемент.** Уже было со слайсами на первой неделе, теперь то же со структурами. Нужен `for i := range`.

**Позиционный литерал структуры.** `Item{1, "x", false}` перестанет компилироваться — или, хуже, начнёт молча путать поля — при изменении структуры. Всегда с именами полей.

**Разыменование `nil`-указателя.** `var l *List; l.Add("x")` — паника во время выполнения. Метод с ресивером-указателем можно вызвать на `nil`, если внутри не трогать поля; на практике проще всегда возвращать инициализированный указатель из конструктора.

**Экспорт всех полей по привычке.** Если поле можно менять только через метод — пишите его с маленькой буквы. Это единственный механизм инкапсуляции в Go, и он работает на уровне пакета, а не типа.

## Если осталось время

Посмотрите на встраивание структур — способ переиспользования, который в Go заменяет наследование:

```go
type Base struct {
	ID        int
	CreatedAt time.Time
}

type Item struct {
	Base           // встроено, без имени поля
	Title string
}

it := Item{}
it.ID = 1          // поле Base доступно напрямую
fmt.Println(it.Base.ID)  // и так тоже
```

Разберитесь, что это **композиция, а не наследование**: `Item` не является `Base`, полиморфизма тут нет. Механизм полезный, но им злоупотребляют — если тянет построить иерархию встраиваний на три уровня, почти наверняка нужен интерфейс.
